# CS2 赛事通知

按各条规则设定的间隔或 Cron 检查 Liquipedia 或 PandaScore 赛程，筛选关注队伍与赛事等级，并向指定 QQ 会话发送通知。

可选渠道只有 Liquipedia（默认）和 PandaScore。旧设置中的「未接入」或「自定义 HTTP 接口」会转为 Liquipedia；若旧设置曾启用，迁移时会先关闭通知，需检查筛选条件后重新启用。自定义接口仍需定义比赛数据契约，见[待解决事项](../../docs/notes/cs2-notification-open-items.md)。

## 配置与操作

数据源、关注队伍、等级和目标会话由本模组共用。目标会话可同时选择群聊和私聊，最多 20 个；不选择时继承[整组全局默认目标](../../README.md#全局默认目标会话)，单独选择则由模组目标组整体覆盖全局设置。队伍留空时不按队伍筛选；等级留空时不按等级筛选。

渠道标记决定生效的等级类型：Liquipedia 提供 Valve Tier，使用 Major、Tier 1、Tier 2、Wildcard；PandaScore 不提供 Valve Tier，使用它自行评定的 S/A/B/C/D。两套等级不能互相换算。Liquipedia 的 Valve 等级从赛事页面读取，分阶段页面未标注时读取主赛事页面；仍无法确认等级的赛事不会匹配已选的 Valve Tier。升级前保存的 Liquipedia 配置继续按旧规则（Liquipedia Tier 或 Valve Tier 任一匹配）运行；若只有 Liquipedia Tier 筛选，保存时仍保留旧规则，直到选择 Valve Tier 或主动清空旧等级。完成后只按 Valve Tier 筛选。

PandaScore API Key 在选择该渠道后填入数据源区域，使用独立的宿主凭证引用 `QQBOT_DISPATCH_CS2_MATCHES_PANDASCORE_API_KEY`，不会写入功能状态文件或回显。Liquipedia 原有凭证引用保持不变。切换渠道只切换当前使用的凭证，不会删除另一渠道的 Key；切换回来时可直接看到该渠道是否已配置，只有点击「清除」并保存才会删除当前渠道的 Key。PandaScore 请求使用服务端 Bearer 认证；其 CS2 接口沿用 `/csgo/` 路径。两个渠道共用「配置」页的全局数据源请求超时，默认 30 秒，可设置 5–120 秒。渠道切换后，已通知记录按来源区分；PandaScore 的来源 Tier 不会启用 Liquipedia 的 Valve Tier 设置。

每条规则按目标顺序处理。已通知记录按目标分别保存；一个目标失败时其余目标继续，之后「立即检查」仅补发尚未成功的通知。「立即发送」会对当前目标组逐个重发。结果中的「已提交服务回合」或「已调用上游发送」不代表 QQ 客户端已送达。

每日汇总、赛前提醒与赛果提醒各有开关、检查计划、下次执行时间、运行结果和立即操作，可以同时启用。同一场比赛可以先进入每日汇总，开赛前收到提醒，完赛后再收到赛果。模组总开关关闭时，规则都不会自动运行。新配置只预选每日汇总，模组总开关仍默认关闭；旧配置升级后只保留仍存在的原规则。若旧配置只使用已移除的通知方式，三条规则均保持关闭，需手动启用所需规则。

| 通知规则 | 发送范围 | 默认检查计划 |
| --- | --- | --- |
| 每日汇总（新配置默认） | 按当前时区（默认 `Asia/Shanghai`）汇总今日或明日赛程；同一来源、同一日期最多自动发送一次。仅包含检查时当前渠道可见的赛事，之后新出现的赛事不会自动补入已发送的汇总。内容较长时会分段发送。 | 每天 18:00 的 Cron（默认） |
| 赛前提醒 | 赛事开赛时间进入“最多提前提醒”窗口后，在首次检查时发送一次；开赛后不补发。提前量可设为 15–360 分钟，默认 60 分钟。已通知的对局若改时间，会另外显示旧时间、新时间及提前／推迟；改期后仍在窗口内时，不再重复发送普通赛前提醒。推迟至窗口外但在未来 48 小时内，也可在检查时通知。 | 每 15 分钟检查，初始关闭 |
| 赛果提醒 | 仅发送当前渠道已明确标记完赛、双方比分有效且开赛时间在最近 6 小时内的比赛；进行中比分、无比分及 `0:0` 不发送。按场次去重，手动「立即发送」可重发符合条件的赛果。Liquipedia 渠道保留基于赛事页面的瑞士轮完结通知与有限范围轮次回顾；PandaScore 渠道不推断轮次完成。 | 每 15 分钟检查，初始关闭 |

检查计划只决定何时读取赛程，不决定通知包含哪些比赛。例如 `0 18-23 * * 1-5` 会在工作日 18:00–23:00 每小时检查一次；每日汇总仍只在该日期首次成功检查时发送。三条规则的计划可分别调整。

多条规则同时到期时，自动检查按「赛前提醒 → 赛果提醒 → 每日汇总」的优先级进行。前一条规则确实提交或发送了通知后，下一条至少等待 30 秒，并在间隔到期后的下一次调度检查中继续处理；没有匹配内容的检查不占用间隔。待检查的规则会保存在配置中，重启后继续处理，超过 1 小时的待检查项会失效。赛果提醒按原到期时间判断 6 小时窗口，避免仅因错峰而漏发。服务回合的实际到达顺序仍由上游决定，间隔只约束插件提交时间；同一规则生成多条消息时仍可能连续出现。手动操作不受该间隔限制。

| 操作 | 效果 |
| --- | --- |
| 立即检查 | 在对应规则中按已保存的设置处理尚未通知过的匹配赛事。 |
| 立即发送 | 在对应规则中先保存当前配置，再重发匹配赛事，包括已通知过的赛事。 |

页面显示匹配数量与发送或提交数量。发送失败的赛事不会被记录为已通知；服务回合提交成功仍不代表 QQ 已送达。

## Cron 规则

每条通知规则可分别选择间隔或 Cron。检查间隔可设为 1–1440 分钟。Cron 表达式使用独立输入框，以数组保存。页面会解释表达式，并显示按设定时区计算的下一次执行时间；修改后需保存才会更新。

支持五段格式「分 时 日 月 周」、`*`、`*/步长`、数字列表和范围。日期与星期同时指定时须同时满足。旧版以 `;` 分隔的规则仍可读取，保存后转为数组。

## 内容生成方式

「固定赛事内容」（默认）提交已排版的赛事正文；「AI 焦点分析」使用相同的赛事正文，在末尾添加 1–4 条看点。每日汇总、赛前提醒和赛果提醒都在设置页提供内容示例，不提供自定义 Markdown 模板。Agent 可用 `tools/search` 检索通知生成时过去 30 天的相关新闻与信息，再用 `tools/fetch` 打开原始页面核实事实、日期和规则；任一工具不可用或核实失败时仅依据本次赛事数据，不引用搜索摘要。看点关注战队与选手对阵、赛事阶段、Valve Regional Standings（VRS）排名或积分、晋级条件与后续大赛参赛资格。涉及积分与资格时须核对官方排名、赛制和邀请规则，注明来源链接及发布日期；无法核实就不推断。Valve Tier 赛事分级不等于 VRS 排名或积分。

固定内容按通知用途分别排版：每日汇总按赛事分组列出当天比赛；赛前提醒以「即将开赛」对阵卡展示同赛事的对局、开赛时间和可用的 Bo 信息；赛果提醒显示已确认比分，比分不等时标出胜者，比分相等时只显示比分。数据源提供轮次时展示 Stage／Round，并标明配置时区。Liquipedia 通知显示 Valve Tier，PandaScore 通知显示 PandaScore Tier；无法确认时标为「未確認」。通知按实际渠道署名；Liquipedia 保留 CC BY-SA 3.0 标注，不生成比赛过程或胜负原因。设置页预览与实际发送使用同一套排版。

改期检测依赖已成功提交／调用发送的每日汇总或赛前提醒记录，并随赛前规则检查；若赛前规则关闭、数据源不含可靠轮次或比赛首次出现前未发送过通知，就不会产生改期通知。提前到检查时间之前但仍在最近 6 小时内、且尚未标记完赛的改期也会报告。赛事卡的同轮对局用不含开赛时间的标识去重；旧记录没有完整识别信息时，升级前已发送的赛前提醒或赛果可能无法关联到改期后的对局。取消、未定新时间等状态目前不从赛事消失推断。「Round N 已结束」仅适用于阶段页可确认全部槽位的 16 队瑞士轮；轮次回顾只统计检查时来源列表可见的对局，不代表本轮全部比赛。两种通知设置了关注队伍时都只列对应对局和胜者。

赛果分析以已确认比分为准；比赛过程只有经可靠来源核实后才能提及，不得把搜索摘要或未确认赛况当成事实。旧配置中的自定义模板字段仍可读取，但不再用于生成通知；内容生成方式设置仍会保留。全局切换到直接发送 Markdown 时，页面显示三种固定内容示例，只发送固定赛事正文。投递方式见[根目录说明](../../README.md#全局投递配置)。
