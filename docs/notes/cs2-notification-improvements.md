# CS2 Major 通知改善記錄

建檔日期：2026-11-25。各項實測與回放在對應章節標明日期。

## 依據與目標

2026-11-24 群聊實際收到 13 條通知。使用者將這 13 條以聊天記錄形式轉發到 QQ Bot 私聊；QQ 私聊顯示 13 條，但對應的 DSH 會話顯示 26 條，後 13 條與前 13 條相同。因此，這份 26 條記錄不能當成群聊重發的證據。PVISION 等對局改時間後，群裡只看到新的「即將開賽」。比賽結果分散，沒有輪次脈絡。

目標是讓觀眾快速知道：何時開賽、時間是否變更、目前是哪一輪、已確認什麼賽果。所有內容只使用來源可確認的資料；「已提交服務回合」不等於 QQ 已送達。

- [x] 已向目標會話通知過的比賽發生改期時，顯示舊時間、新時間、提前／推遲及時區；連續改期只發最新變更，不重複發一般賽前提醒。

### 低／資料前提

其餘項目只記在[CS2 賽事通知待解決事項](./cs2-notification-open-items.md)；完成後從待解決清單移除，並在本文件記錄結果。目前的賽事列表不提供可核實的取消或晉級表；其他賽制不以推測實作。

### 2026-11-25 賽事輪次 API 實測

以 `PGL/2026/Singapore` 為例，接口基址為 `https://liquipedia.net/counterstrike/api.php`。使用本模組的 User-Agent，遵守 [Liquipedia MediaWiki API 條款](https://liquipedia.net/api-terms-of-use) 的一般請求間隔至少 2 秒、`action=parse` 至少 30 秒。以下均為實際 HTTP 請求結果，未抓取非 API 網頁：

| 接口／資料 | 實測 | 對輪次的用途與限制 |
| --- | --- | --- |
| Liquipedia `action=query&prop=links`，主賽事頁 | HTTP 200；回傳 419 個連結，其中有 Stage 1、2、3 和 Playoffs 頁 | 可發現分階段頁面；需篩選同賽事標題，不能把所有連結當階段。 |
| Liquipedia `action=query&prop=revisions&rvslots=main&rvprop=content`，主頁與 Stage 1／2／3／Playoffs | 均 HTTP 200。Stage 1 原始 wiki text 包含 `SwissStandings`、Round 1–5 的 `Matchlist`；Playoffs 包含四場八強、兩場準決賽、一場決賽，以及三四名賽槽位 | 是目前最有價值的來源：包含完整對陣槽位、隊伍、日期、比分和 `finished` 欄位，但結構為 wiki 模板，並非規範化 JSON。 |
| Liquipedia `action=parse&prop=sections`，Stage 1 | HTTP 200；回傳 `Detailed Results`、Round 1–5 及 High／Mid／Low 小節索引 | 能定位輪次；小節索引可能隨編輯變動，不能寫死。 |
| Liquipedia `action=query&prop=revisions&rvsection=<索引>`，Stage 1 各輪小節 | HTTP 200。Round 1 有 8 個 `Match`；Round 2 高／低各 4；Round 3 高／中／低分別 2／4／2；Round 4 高／低各 3；Round 5 有 3 個，共 8／8／8／6／3 場槽位 | 能計算當前頁面列出的完整輪次槽位。Round 4、5 的隊伍仍為空，不能當作已排定對陣；瑞士輪後續配對會變動。 |
| Liquipedia `action=parse&prop=text`，Stage 1 | HTTP 200；回傳約 330 KB 渲染結果，當時有 16 個 `data-finished="finished"` 標記 | 可核對已完成的比賽；成本高、HTML 解析脆弱，優先考慮原始 wiki text。 |
| PandaScore `/csgo/tournaments/running` 與 `/tournaments/1/brackets` | 均 HTTP 403，回傳 `Token is missing` | [官方文件](https://developers.pandascore.co/docs/getting-started)列有賽事比賽、積分與淘汰賽對陣接口；未配置 token，無法實測本屆資料覆蓋或輪次完整性。`/csgo/` 是其 CS2 路徑。 |

[LiquipediaDB API](https://liquipedia.net/api-terms-of-use) 須先申請並取得 API Key，現有環境沒有憑證，未實測回傳。[GRID Open Access](https://grid.gg/open-access/) 亦須申請；其主要價值是比賽內逐回合資料，不能把地圖內 Round 直接當成賽事瑞士輪 Round。HLTV 等非正式抓取接口不納入目前方案。

**結論與實作：** 前述「賽事列表不提供完整輪次」仍成立，但分階段頁面的正式 MediaWiki API 為本屆 Major 提供了可用的輪次槽位。賽果檢查讀取對應 Stage 頁的原始 wiki text；只對 `swiss3` 的 16 隊瑞士輪按 8／8／8／6／3 個槽位驗證，且要求每個槽位有確定隊伍、比賽完賽標記及可判勝負的已完賽地圖比分。確認後使用獨立的 `roundcomplete:` 記錄只通知一次；失敗不標記，下次可重試。資料不完整時沿用有範圍說明的回顧。其他賽制模板、缺席／棄權、資料延遲和頁面修訂仍需額外驗證，不輸出未證實的晉級資訊。

## 完成狀態

CS2 通知改善中，原定高、中優先級項目及 16 隊瑞士輪的「Round N 已結束」已實作。取消／延期狀態、其他賽制的完整輪次和晉級資訊仍缺可靠資料。聊天記錄轉發後 DSH 私聊會話內容翻倍屬獨立的入站問題，已提交上游 [dsh-qqbot #140](https://github.com/tencent-connect/dsh-qqbot/issues/140)；本插件不針對該現象修改 CS2 通知邏輯。

### 13 條歷史通知回放

使用者提供的前 13 條實際群聊通知中：第 1 條列出 Stage 1 首輪 8 場；第 3、6、8、9、10、12 條分批確認 2／2／1／1／1／1 場賽果；第 11 條已出現次輪對陣，但此時首輪只確認 7 場，第 12 條才補齊第 8 場。其餘第 2、4、5、7、11、13 條為賽前提醒。當時通知沒有 Stage／Round 與 Valve Tier；PVISION 的賽前時間先後顯示 14:00、14:15、14:25，沒有明說改期，使用者難以分辨新舊提醒。

本地回放依這 13 條的順序逐步建立 8 場首輪賽程和已知賽果，並重建每一步對應的階段頁完賽標記；發送器使用替身，沒有發往 QQ。結果：前 7 場賽果及第 11 條次輪對陣出現時都沒有「Round 1 已結束」；第 12 條補齊第 8 場後發送一次；第 13 條再次檢查沒有重發。這是依歷史通知內容重建的流程測試，原記錄不含逐次 API 快照與精確發送時間，不能反推當時 Liquipedia 頁面的實際更新時間。

## 會話記錄數量補充

群聊的 13 條通知經使用者手動以聊天記錄形式轉發至 QQ Bot 私聊後，QQ 私聊顯示 13 條，DSH 對應私聊會話顯示 26 條。問題發生在轉發訊息的入站／會話呈現鏈路，與 CS2 模組發送 13 條群聊通知是兩個方向。使用者確認 11 月 24 日及目前均使用全局「直接發送 Markdown」；這只能說明原始群聊通知的發送方式，不能解釋私聊入站翻倍。本插件未實作 QQ 入站消息的會話寫入；`upstream-sender.js` 對 `handleInboundMessage` 的包裝只保存 Bot 實例，並將原方法調用一次。目前無法單憑畫面判定是 QQ 回調重複、上游 QQ Bot 對轉發消息重複處理、DSH 持久化重複，還是會話畫面重複呈現。

此問題已提交上游 [dsh-qqbot #140](https://github.com/tencent-connect/dsh-qqbot/issues/140)。若上游需要進一步定位，可匯出該 QQ Bot **私聊**對應 DSH 會話的原始 session log，對照重複內容的事件 `seq`、`type`、`data.id`、`data.source` 與時間：若 log 只有 13 條而畫面有 26 條，查 DSH 畫面／歷史分頁；若 log 有 26 條，再看是否成對共享 QQ 訊息 ID，以及是否均由 QQ Bot 入站來源寫入。要再區分 QQ 官方回調與上游 QQ Bot 處理，還需同一時間段的原始入站事件 ID 或上游調試紀錄。匯出檔可能包含完整會話與附件，分享前需檢查敏感內容。

## 實作約束

既有每日匯總、賽前與賽果三條規則保留。改期檢查隨賽前規則執行；未開啟賽前規則時不宣稱即時追蹤改期。舊資料中的 timestamp 型 ID 保留識別支援，但舊紀錄沒有賽事頁／輪次資訊，無法全面還原成新識別鍵；舊賽前提醒與賽果紀錄遇改期都可能再次通知。發送失敗不更新通知狀態。固定通知與服務回合都應用相同事實資料與來源標註。一般輪次回顧只節選至多四位勝出隊伍；確認整輪結束後最多列出當次可見的八位勝者，後續對局最多列兩場，避免訊息過長。
