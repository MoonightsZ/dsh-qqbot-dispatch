# 偶尔闲聊话题池设计

状态：已确认并实施；实际运行仍需在配置好模型的 DSH 环境中验证。

## 目标与边界

- 用户输入一个主题词，请 AI 推荐多条不同、可直接发送的闲聊开场白；用户逐条选择后才加入话题池。
- 话题以列表管理，每条可属于多个标签。保留生成时的主题词，方便再次生成和追溯。
- 自动发起和“立即发起”使用同一话题抽取规则。全局投递方式为“直接发送 Markdown”时，发送已保存话题的原文；服务回合方式仍将话题作为生成提示。
- AI 推荐只在设置页按用户操作触发，不通过 QQ 会话的服务回合生成候选，不自动保存或发送候选。
- 本次调整话题抽取；每日检查、触发概率、冷却和安静时段留待已记录的独立讨论。

## 已考虑的方式

| 方式 | 取舍 |
| --- | --- |
| 保留分隔文本，增加 AI 填入文本框 | 改动小，但难以逐条确认、管理标签和避免重复。 |
| 话题列表与手动触发 AI 推荐 | 选择此方案。候选先预览、再手选入池；配置和发送边界清楚。 |
| AI 在每次发送时即时生成话题 | 不适合直接发送模式的可预览性，也增加定时运行时对模型的依赖。 |

## 数据与迁移

每条话题保存 `id`、`text`、`tags: string[]`、`sourceKeyword` 和 `enabled`。`sourceKeyword` 仅记录生成来源，不自动充当标签；AI 候选入池时默认附上同名标签，用户可修改或增加其他标签。手动新增的话题可留空来源。标签去重并修剪空白；话题文字、标签数量和列表总量由服务端设定明确上限，不能沿用当前整个文本框共 120 字的限制。

旧 `topics` 字符串按现有 `|` 或换行规则拆分，逐条迁移为启用、无标签的话题，保存时转为结构化列表。读取和执行路径应兼容尚未迁移的状态文件。旧自定义话题继续取代内置话题；仅当话题池真正为空时，使用三个内置话题作为后备。若列表有条目但全部禁用，跳过发送并显示原因，不偷偷回退到内置话题。

## 设置页

1. 输入主题词，点击“AI 推荐”；展示几条不同的完整开场白，每条可预览、编辑、勾选。
2. 点击“加入话题池”后，勾选的话题成为待保存配置；页面保存成功后才参与定时和手动抽取。
3. 话题列表支持手动添加、编辑文字、启停、删除和编辑多个标签；可按标签筛选，显示每条话题的来源主题词。
4. “立即发起”沿用现有先保存再执行的流程；直接发送模式在设置页说明会原文发送所抽取的话题。
5. AI 推荐失败时保留输入与已有列表，并给出错误；手动编辑不依赖 AI。

## 抽取规则

仅使用启用且文字有效的话题。无标签话题进入虚拟“未分类”标签；同一条话题在池中只存一份。

1. 若存在至少两条不同候选，先排除上次成功提交投递链路的话题；否则允许重复。
2. 从仍有候选的标签中等概率选一个。
3. 在所选标签内随机选话题；话题的权重与其当前有效标签数成反比，减轻多标签话题因进入多个抽取集合而获得的额外机会。此规则优先平衡标签，不保证每条话题等概率。
4. 投递链路成功后记录话题 ID。服务回合“已提交”和上游发送“已调用”沿用现有结果语义，均不宣称 QQ 客户端已送达。

随机源可注入测试；测试覆盖旧配置迁移、空池与全禁用池、多标签权重、上次话题排除，以及两种投递模式的消息内容。

## AI 接入约束

当前插件没有设置页专用的模型推荐接口。实施时先核对当前 DSH 提供的模型调用接口，再在插件服务端提供受限的推荐请求；仅将用户输入的主题词和必要的生成指令交给模型，不读取 QQ 会话内容或凭证。限制单次候选数量、输入与输出长度，并在服务端校验、去重。模型不可用时明确提示，话题池手工功能保持可用。

## 验收要点

- 输入一个主题词可得到多条候选；未选择、未保存的候选不会参与发送。
- 一条话题能保存多个标签；筛选和抽取不会复制话题数据。
- 自动与手动执行采用相同算法；多标签话题不会仅因标签数量而线性增加发送机会。
- 旧配置原有话题不丢失；直接发送模式只发送所选话题原文。
